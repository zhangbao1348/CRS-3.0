# 数据及报表 (Data & Reports)

数据及报表模块是 CRS 系统的运营决策中枢，负责对全渠道订单数据、酒店客房产出、分销效率进行跨维度的统计和分析。通过提供实时的同环比对比、数据下钻透视及多层级报表导出，为集团和酒店的管理层提供数据化决策依据。

---

## 1. 核心业务指标与统计口径定义

为了确保财务账目与运营报表的一致性，系统各报表必须严格遵循以下业务指标计算口径：

### 1.1 间夜数 (Room Nights)
* **业务定义**：订单中所有生效房间在住店期间产生的“房间 $\times$ 晚数”总和。
  $$\text{间夜数} = \text{订单预订房间数 (room\_count)} \times \text{入住晚数 (nights)}$$
  *(例如：某订单预订 3 间标准双床房，入住 2 晚，计为 6 间夜)*
* **状态过滤规则**：
  * **计入**：仅统计业务状态为“已确认（confirmed）”、“已入住（checked_in）”、“已离店/已完成（completed/checked_out）”的有效订单。
  * **剔除**：**已取消（`cancelled`）和未入住（`no_show`）的订单不计入任何间夜数统计**。

### 1.2 订单总金额 (Total Revenue / Room Revenue)
* **业务定义**：指客房售卖产生的含税房费总额（包含增值税与服务费快照，但不包含单独结算的客房外增值消费）。
* **退改损失处理**：
  * 若有效订单已离店或已确认，其房费按 100% 计入总金额。
  * 若订单取消，房费不计入总金额；但若因违反取消政策扣除了“担保金/取消违约金”，该款项应在报表“违约金收入”中单列，不直接并入常规客房房费收入中，避免污染平均房价指标。

### 1.3 间夜平均价 ADR (Average Daily Rate)
* **业务定义**：酒店在特定时间段内，售出客房的平均每日房价。
* **计算公式**：
  $$\text{ADR} = \frac{\text{特定维度下的客房总金额}}{\text{对应有效间夜数}}$$
* **防污染规则**：ADR 计算必须使用排除违约金后的**纯净客房收入**除以**有效间夜数**，防止已取消订单的违约金虚增 ADR，误导定价策略。

### 1.4 订单支付总积分数 (Points Redeemed)
* **业务定义**：会员在使用“积分兑换”或“积分+现金”预订时，消耗的 CRM 积分总量。该指标用于核算集团 CRM 营销成本。

### 2.2 多层级嵌套分组展示（数据魔方）
报表结果通过 Ant Design 嵌套折叠 Table 展示。
* **分级展示**：根据“分组依据 1”与“分组依据 2”的选择，报表自动进行分组聚合。
  *(例如：分组 1 为“渠道”，分组 2 为“酒店”。表格第一列按“渠道”合并单元格；第二列展示该渠道下有订单的“具体酒店”行；后续列展示对应数据。)*
* **未分组（可空）兼容**：
  * 若“分组依据一”和“分组依据二”均未选择，则报表只展示一行“全局数据-全部订单”的全局汇总。

* **数据列定义**：
  * **本期数据**：展示本期日期段内的【订单数（单）】、【订单总金额（CNY）】、【订单支付总积分数】、【间夜数】、【间夜平均价 ADR】。
  * **对比期数据**：对应展示对比期内的以上 5 个指标。
  * **变化指示器**：在每一项本期指标右侧，高亮显示增长率。
    * 增长率算法：$\text{增长率} = \frac{\text{本期值} - \text{对比期值}}{\text{对比期值}} \times 100\%$。
    * UI 展现：增长时显示绿色朝上箭头及比例（如 `↑15%`），下降时显示红色朝下箭头及比例（如 `↓8%`），无变化显示灰色。

### 2.3 报表下钻审计 (Drill-Down to Order Details)
* **操作入口**：报表每行末尾提供“查看订单明细”按钮。
* **业务流向**：点击后，系统在新窗口打开订单管理页面。
* **过滤透传**：系统自动将当前行的**“酒店编码”**、**“渠道编码”**、**“市场/房型/房价码”（若有）**及**“查询时间段”**以 URL 参数或状态形式透传给订单列表，直接筛选出支撑这一行统计数字的原始订单明细。便于财务人员在发现数据异常（如 ADR 偏低）时，快速追查到具体的特价订单。

## 3. 出租率报表 (Occupancy Reports) [已实现]

出租率报表是反映酒店资产运营效率与客房供需平衡状态的“晴雨表”，用于支持集团及单店收益管理人员（Revenue Manager）进行动态房价调整与房控决策。

> [!NOTE]
> **产品化迭代说明 (2026-06-07)**：
> 1. **核心计算容错**：优化了跨月天数计算的底层逻辑，支持根据所选月份动态计算精确的单月天数（自动适配平年、闰年及大月小月天数差异），消除日期计算崩溃风险。
> 2. **数据源白盒化**：移除了全部前端静态 Mock 演示数据，100% 对接后端实时房态与预订明细汇总接口，确保报表数据的财务审计级准确度。

### 3.1 收益决策过滤条件
为了支持运营人员灵活切换分析视域，页面顶部设计了实时联动筛选区：

| 字段名称 | 交互类型 | 业务定位与过滤口径 |
| :--- | :--- | :--- |
| **选择酒店** | 下拉单选 | 默认展示“全集团”，支持切换至某一具体酒店。选项列表仅展现当前租户下已启用的活跃酒店。 |
| **统计维度** | 下拉单选 | 选项包括：<br>1. **按酒店维度**：统揽各酒店整体的使用率；<br>2. **按房型维度**：下钻分析细分物理房型（如高级双床房、豪华套房）的出租表现，以便发现结构性滞销或热销房型。 |
| **统计月份** | 月份选择器 | 支持选择历史及当前月份，系统将按该月份的实际天数自适应拉取数据。 |

### 3.2 房态与出租率分析矩阵 (Grid Matrix)
报表以高密度的水平网格矩阵展示所选月份内每日的房态明细，支持横向 `3200px` 超长滚动适配：

* **日期自适应天数表头**：表头列按月份实际天数（1-31天）动态生成。每列双行展示：上行展示日期（格式 `MM-DD`），下行标注星期几。对于不包含 31 号的月份（如 2 月、4 月、6 月等），超出当月实际天数的列自动呈现为灰色占位符 `—`，以维护表盘整体一致性。
* **多维交叉与单元格合并**：
  * **按酒店维度**：首列为“酒店名称”（根据相邻行相同酒店做 `rowSpan` 合并）；次列为“指标类型”。
  * **按房型维度**：首列为“酒店名称”（合并）；次列为“物理房型”（根据同一酒店下的具体房型进行 `rowSpan` 合并）；第三列为“指标类型”。
* **指标类型运营口径**：
  每个细分统计维度在纵向上拆分为 4 行关键经营指标：
  1. **物理库存**：酒店/该房型当天在系统内登记 的 总物理房间数（已剔除 OOO 长期维修房）。
  2. **已卖房**：当天已预订的有效房间天数总和（对应“已确认”、“已入住”、“已离店”状态的订单间夜数）。
  3. **订单数**：当天产生有效预订的订单笔数。
  4. **出租率**：当天客房的利用率。计算公式为：$$\text{出租率} = \frac{\text{已卖房}}{\text{物理库存}} \times 100\%$$
* **视觉预警与极端情况处理**：
  * **爆满高光**：当某日的出租率 `> 85%` 时，数值颜色自动变更为**深绿色（`#389e0d`）**并加粗，帮助运营人员快速识别满房的高峰期。
  * **超卖兼容**：若系统启用了超预订策略，且某日实际预订超卖（已卖房 > 物理库存），出租率允许显示超过 100%，以准确反映超卖收益现状。

## 4. 营收报表 (Revenue Reports) [已实现]

营收报表用于直观反映酒店在一段时间内的日级资金产出效率与平均房价水准，是评估价格计划（Rate Plan）定价合理性及收益最大化的核心依据。

> [!NOTE]
> **产品化迭代说明 (2026-06-07)**：
> 1. **双维决策模式**：为了满足不同决策习惯，新增了“表格数据模式”与“图形趋势模式”的一键切换。
> 2. **数据可视化赋能**：引入 Ant Design Plots 图表库，直接以双折线走势图立体对比每日的订单量和房价波动。
> 3. **高保真数据联动**：彻底停用 Demo Mode，报表数据直接映射自后端的聚合决策表，满足日结与财务审计的对账要求。

### 4.1 表格明细模式 (Grid View)
以每日经营明细表形式直观呈现客房销售金额和单数：
* **统计指标行**：每个维度纵向拆分为 2 行核心指标：
  1. **总订单数**：当天成交的有效订单总量（单）。
  2. **平均房价 (ADR)**：当天平均每日售房含税均价。计算公式为：$$\text{ADR} = \frac{\text{客房总房租收入 (不含已取消违约金)}}{\text{有效间夜数}}$$
* **财务级数据呈现**：
  * “平均房价”行标题应用蓝色加粗标注。
  * 均价数据单元格统一使用等宽的 `Consolas` 字体，且前缀人民币符号（如 `¥450`），保持财务数据的严谨对齐与易读性。
  * 自适应日期列与行合并机制与出租率报表保持完全一致。

### 4.2 图形趋势模式 (Visual Chart View)
图形模式下，系统在垂直方向平铺展示两个跨维度的折线对比图：

#### A. 每日订单量趋势折线图
* **业务定位**：直观对比当月每天的客房预订活跃度，展现分销波峰波谷。
* **展现细节**：横轴为日期（`MM-DD`），纵轴为订单量（单位：单）。
* **多维图例对比**：每条折线代表一个统计维度（如“南京金陵饭店 - 豪华大床房”）。

#### B. 平均房价 (ADR) 走势折线图
* **业务定位**：监控房价随供求关系波动的曲线，用于评估动态定价机制的灵敏度。
* **展现细节**：横轴为日期，纵轴为平均房价（单位：元）。

#### C. 图形交互特性与体验优化
* **跨线多维悬浮框 (Shared Tooltip)**：鼠标移至某一天时，悬浮框内同时排列该天所有酒店/房型的具体数值，方便收益分析师进行横向对比与竞争性诊断。
* **数据标记锚点 (Markers)**：折线图上的数据节点高亮呈现，便于快速感知极端高价或低价节点。
* **空状态优雅降级**：无有效运营数据时，图表区域平滑降级，显示“暂无趋势数据”的轻量化 Empty 状态。

## 6. 全系统 AI-Ready 诊断与决策追踪 (AI-Ready Diagnostics & Trace) [已实现]

为了实现系统级故障与非异常业务争议（如“下单成功但价格与预期不符”）的白盒化快速定位，系统构建了 AI-Ready 诊断追踪与决策溯源底座，允许 AI 通过唯一的链路 ID（`traceId`）直接定位到相关代码层级与业务参数快照。

### 6.1 链路追踪标识 (Trace ID) 规范
* **全局唯一性**：每次 HTTP 调用由前端自动生成 32 位 UUID 附加在 `X-Trace-Id` 请求头，或由后端拦截器在入口生成。
* **跨线程/异步传递**：基于 SLF4J MDC 与 ThreadLocal 在线程内传递 traceId，在日志中自动打印。对于异步定时任务（如超时自动取消），在任务启动时为每笔订单分配独立的 traceId，实现细粒度追踪。

### 6.2 决策快照 (DecisionSnapshot) 核心打点
系统在以下关键业务节点执行时，动态收集决策中间值，并以 JSON 格式持久化在 `SystemTraceLog` 的 `decision_snapshot` 中：

| 业务节点 | 决策收集内容 (DecisionSnapshot 键名与参数) | 关联 PRD 文档 |
| :--- | :--- | :--- |
| **预订下单 (Create)** | 查出的全部 `HotelPrice` 原始数据、酒店保底价触发状态、多税率分解税额（VAT/SERVICE）、输入价与系统计算价的对账对比细节。 | `10-价格计划管理.md`, `14-订单管理.md` |
| **可用性检查 (Check)** | 房态开启/关闭维度详情、预订控制校验（最小/最大入住天数）、PMS 库存可售数、各层级配额扣减剩余。 | `11-库存管理.md` |
| **支付确认 (Pay)** | 悲观锁获取时间、支付流水号防重幂等校验、对账金额对比快照。 | `14-订单管理.md` |
| **自动取消 (Cancel)** | 判定支付超时扫描的时间戳、支付截至时间对比、批量取消结果。 | `14-订单管理.md` |

### 6.3 前端报错自动收集与上报
* **自动监听**：全局监听 `window.onerror` 以及 `unhandledrejection`（Promise 拒绝）。
* **上下文关联**：自动捕获 JS 错误堆栈、出错文件名、行列号、当前路由，并从 sessionStorage 中读取最近一次 HTTP 请求的 `crs_last_trace_id` 关联上报至后端。

## 7. 大数据量报表高性能预聚合与同步对账设计规约 (High-Performance Aggregation & Reconciliation) [已实现]

为了确保报表系统在千万级订单体量下依旧实现毫秒级响应，系统建立了“多级加速与日聚合维度汇总表”技术架构，将多维分组聚合的计算耗时由运行期的 `100ms+` 骤降至 **2~5ms**。

### 7.1 预聚合维度汇总表设计 (`report_daily_reservation_summary`)

系统对订单按天和核心业务的最细物理叶子节点进行预折叠。为确保报表可以直接对“订单状态”与“房价大类”做单表闪电统计而不触发额外的 `LEFT JOIN rate_plans` 联表开销，在此汇总表中冗余了“订单状态”和“房价大类编码”字段。

| 字段名 | 类型 | 说明 | 索引类型 |
| :--- | :--- | :--- | :--- |
| **id** | INT (PK) | 自增主键 | Primary Key |
| **tenant_id** | INT | 租户 ID | Unique Key / Index |
| **report_date** | DATE | 统计日期 (对应创建日期 `created_at` 的天) | Unique Key / Index |
| **hotel_code** | VARCHAR(50) | 酒店编码 | Unique Key / Index |
| **channel_code** | VARCHAR(50) | 渠道编码 | Unique Key / Index Merge |
| **market_code** | VARCHAR(50) | 市场编码 | Unique Key / Index Merge |
| **rate_category_code**| VARCHAR(50) | 房价大类编码 (冗余大类维度，免联表 Join 加速) | Unique Key / Index Merge |
| **rate_plan_code** | VARCHAR(50) | 价格计划编码 (叶子节点价格码，支持明细下钻) | Unique Key / Index Merge |
| **room_type_code** | VARCHAR(50) | 房型编码 (支持房型占比分析) | Unique Key |
| **reservation_status**| VARCHAR(30) | 订单状态 (包括 confirmed-已确认, checked_in-已入住, completed-已离店, cancelled-已取消) | Unique Key / Index |
| **order_count** | INT | 订单总单数（在该状态下的有效单数） | - |
| **room_nights** | INT | 生效总间夜数 | - |
| **total_revenue** | DECIMAL(12,2)| 客房总含税收入 | - |
| **points_redeemed**| INT | 抵扣的总积分数 (BAR 价格计划下按 1间夜=500积分 折算) | - |

* **唯一联合约束 (`uk_daily_summary`)**：
  `tenant_id, report_date, hotel_code, channel_code, market_code, rate_category_code, rate_plan_code, room_type_code, reservation_status`。该联合唯一键是多维状态预聚合的原子防重基础。
* **联合索引 (`idx_summary_base`)**：
  `tenant_id, report_date, hotel_code`，作为报表必填强约束时间过滤的快速扫描键。
* **单列单维索引 (`Index Merge` 机制)**：
  在 `channel_code`、`market_code`、`rate_category_code`、`rate_plan_code`、`reservation_status` 上各自建立独立索引。支持前端在“非必填、多条件任意组合”的情况下，由 MySQL 在内存中交叉求交集过滤，绝不触发全表扫描。

### 7.2 T+1 历史静态数据对账同步机制 (T+1 Reconciler)
* **执行时间**：每日凌晨 2:00。
* **运行机制**：定时调度器 `ReportDailySummaryScheduler` 自动轮询所有活动租户，覆盖同步“今日与昨日”的数据。
* **业务目的**：重新拉取这两天的 reservation 明细进行覆盖重算，用以抹平因结账延迟、跨天入住或订单滞后回调产生的微小尾差，确保账目 100% 对齐。
* **清洗容错**：聚合清洗原始数据时，对维度空字段应用 `COALESCE(col, 'DEFAULT')` 降维默认值对齐，保证插入鲁棒性。

### 7.3 T+0 实时天级数据重算机制 (T+0 Day-level Recalculation)
* **触发机制**：当订单被创建（`create`）、支付确认（`pay`）、更新业务状态（`updateStatus`）或被取消（`cancel`）时，由 `ReservationService` 发布 `ReservationChangedEvent` 事件。
* **事件消费重算**：
  在 `ReportDailySummaryListener` 中，直接获取变更订单的创建日期 `reportDate` (订单的 `createdAt` 这一天)，调用 `reportService.initializeSummaryData(res.getTenantId(), reportDate, reportDate)` 执行这一天的数据重算。
* **重算优势**：
  * **100% 强一致性**：通过删除当天全部旧汇总记录并基于订单明细重新 GROUP BY 插入，彻底抹平了由于乱序事件、高并发修改状态导致因数加减计算失真的问题。
  * **极速响应**：由于仅重算单日当天的多维汇总，底层 `reservation` 表数据量极小，重算操作仅耗时 1~2 毫秒，对在线业务零影响。
