# CRS 酒店预订实时查询接口 — PRD

> **版本**：v1.1  
> **更新日期**：2026-05-03  
> **使用方**：小程序端  
> **状态**：✅ 已实现

---

## 一、概述

本文档定义了 CRS 中央预订系统面向小程序端的实时查询与预订接口。所有接口通过渠道秘钥（API Key + Secret）进行身份认证，数据按租户隔离。

### 接口清单

| 序号 | 接口名称 | 方法 | 路径 | 状态 |
|------|----------|------|------|------|
| 1 | 查询酒店列表 | GET | `/api/open/hotels` | ✅ 已实现 |
| 2 | 查询酒店详情与价格 | GET | `/api/open/hotels/{hotelCode}` | ✅ 已实现 |
| 3 | 可订检查 | POST | `/api/open/availability/check` | ✅ 已实现 |
| 4 | 创建订单 | POST | `/api/open/reservations` | ✅ 已实现 |
| 5 | 查询订单详情 | GET | `/api/open/reservations/{reservationCode}` | ✅ 已实现 |
| 6 | 取消订单 | POST | `/api/open/reservations/{reservationCode}/cancel` | ✅ 已实现 |
| 7 | 支付订单 | POST | `/api/open/reservations/{reservationCode}/pay` | [ ] 未实现 |

### 公共约定

- **Base URL**：`https://{domain}/api/open`
- **认证方式**：所有请求必须在 Header 中携带 `X-Api-Key` 和 `X-Api-Secret`，对应 `tenant_channels` 表的 `access_key` / `access_secret`
- **数据格式**：JSON（`Content-Type: application/json`）
- **日期格式**：`yyyy-MM-dd`（如 `2026-05-01`）
- **日期边界安全**：所有涉及查询、可订检查和下单的接口，其 `checkInDate` 不允许早于系统允许的最早入住日期。默认最早可入住日为系统当天；每天 `00:00-06:00` 允许把“昨天”作为最早可入住日。单次查询或预订的最大跨度（`nights`）不得超过 **30** 晚，超过则拦截并返回 `400`。
- **金额单位**：人民币元，保留两位小数
- **字符编码**：UTF-8

### 公共响应结构

```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "timestamp": "2026-05-01T10:00:00+08:00"
}
```

### 公共错误码

| 错误码 | 含义 | 触发场景 |
|--------|------|---------|
| 200 | 成功 | 请求处理正常 |
| 400 | 请求参数错误 | 缺少必填项、离店日期早于入住日期、日期格式错误等 |
| 401 | 认证失败 | API Key 无效、Secret 不匹配、渠道状态非 active、渠道未连接 |
| 403 | 权限不足 | 渠道未被授权访问该酒店（channel_hotel_mappings 缺失或状态非 active） |
| 404 | 资源不存在 | 酒店代码无效或酒店状态非 active |
| 409 | 业务校验未通过 | 库存不足、房态关闭、不满足预订控制规则、房型不适用等（详见下文 reason 枚举） |
| 500 | 服务器内部错误 | 后端发生未捕获异常 |

### 接口 1：查询酒店列表

获取渠道可见的酒店列表，包含静态信息和起价。

- **方法**：`GET`
- **路径**：`/api/open/hotels`
- **状态**：[ ] 未实现

#### 请求参数（Query）

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| cityId | String | 否 | 城市筛选，对应 `hotels.city` |
| checkInDate | String | 否 | 入住日期（yyyy-MM-dd），用于计算起价和可用性 |
| checkOutDate | String | 否 | 离店日期（yyyy-MM-dd），与 checkInDate 配对使用 |
| keyword | String | 否 | 搜索关键词，模糊匹配酒店中/英文名称 |
| page | Integer | 否 | 页码，默认 1 |
| pageSize | Integer | 否 | 每页数量，默认 20，最大 50 |

#### 业务规则

1.  **前置校验与过滤**：
    - 仅返回 `hotels.status = 'active'` 的酒店。
    - 仅返回当前渠道在 `channel_hotel_mappings` 表中绑定的酒店（且映射状态必须为 `active`）。
2.  **搜索逻辑细节**：
    - `cityId`：基于 `hotels.city` 的精确匹配。
    - `keyword`：对 `hotels.chinese_name` 和 `hotels.english_name` 执行不区分大小写的 `LIKE %keyword%` 模糊匹配。
3.  **分页限制**：`pageSize` 若超过 50，后台将强制重置为 50。
4.  **实时起价计算**：
    - 若传入 `checkInDate` / `checkOutDate`，系统会检索日期范围内所有有效房型+价格计划的组合。
    - 自动剔除存在 `room_status.is_open = false` 记录的房型。
    - `startingPrice` 取所有组合中 `price_with_tax` 的最小值。
5.  **日期逻辑**：
    - `checkOutDate` 必须晚于 `checkInDate`（不满足返回 400）。
    - `checkInDate` 不允许早于系统允许的最早入住日期；默认最早为当天，每天 `00:00-06:00` 允许昨天。

### 接口 2：查询酒店详情与价格

获取单个酒店的完整信息，包含所有可售房型及每日价格。

- **方法**：`GET`
- **路径**：`/api/open/hotels/{hotelCode}`
- **状态**：[ ] 未实现

#### 路径参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| hotelCode | String | 是 | 酒店编码 |

#### 请求参数（Query）

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| checkInDate | String | 是 | 入住日期（yyyy-MM-dd） |
| checkOutDate | String | 是 | 离店日期（yyyy-MM-dd） |
| adultCount | Integer | 否 | 成人数，默认 2 |
| childCount | Integer | 否 | 儿童数，默认 0 |
| roomCount | Integer | 否 | 房间数，默认 1 |
| memberNo | String | 否 | 会员编号，用于匹配会员专属价格计划 |
| memberLevel | String | 否 | 会员等级（如 silver/gold/platinum/diamond），用于筛选对应等级可见的价格计划 |

#### 业务规则

1.  **准入授权校验 (Hotel Level)**：
    - 实时检查 `channel_hotel_mappings.status`。若映射不存在或状态非 `active`，返回 **403 Forbidden**。
2.  **产品发布过滤 (Product Level)**：
    - **核心逻辑**：系统仅返回已通过「渠道发布」功能发布至该渠道的 `房型 + 价格计划` 组合（查询 `channel_publish_records`）。
    - **展示规则**：若某房型下没有任何价格计划被发布，该房型在响应中将被剔除。
3.  **房型适用性过滤**：
    - 仅返回 `hotel_room_types.status = 'active'` 的房型。
    - 若价格计划定义了 `applicableRoomTypes`（JSON），系统将严格比对房型编码，仅保留匹配的房型。
4.  **价格计划过滤 (Personal Membership)**：
    - **等级匹配**：若 `rate_plans.personal_membership` 不为空（或 `[]` / `{}`），则必须与请求中的 `memberLevel` 匹配，否则不显示。
    - **空值处理**：若请求未传 `memberLevel`，仅显示 `personal_membership` 为空或全开放的计划。
5.  **库存计算逻辑**：
    - `availableRooms` = `MIN(inventory.available_rooms)` 作用于整个 `[checkInDate, checkOutDate)` 区间。
6.  **房态控制层级**：
    - 优先检查 `room_status` 表。若日期范围内任意一天存在 `is_open = false`，该房型在响应中将被标记为不可订（或直接过滤）。
7.  **动态预订控制 (Dynamic Controls)**：
    - **提前预订**：比对当前系统日期与 `checkInDate`，必须满足 `rate_plans.advance_booking_min`（或日期级 `booking_controls`）。
    - **入住天数**：校验连住天数必须落入 `[minimum_stay_min, minimum_stay_max]` 区间。
8.  **政策集成**：
    - 自动聚合 `cancellation_policies` 和 `guarantee_policies` 的多语言描述及结构化字段。
9.  **日期边界限制**：
    - `checkInDate` 不允许早于系统允许的最早入住日期；默认最早为当天，每天 `00:00-06:00` 允许昨天。

#### 业务规则（严格校验链）

系统将按照以下顺序执行串行校验，任一环节失败均返回 409：

1.  **对象存在性与状态**：
    - 校验 Hotel, RoomType, RatePlan 是否存在。
    - 校验三者状态是否均为 `active`。
2.  **房型适用性 (Compatibility)**：
    - 校验 `rate_plan.applicable_room_types` JSON 是否包含当前 `roomTypeCode`。
3.  **会员资格核验**：
    - 若 `rate_plan` 包含会员限制（`personal_membership` 非空）：
        - 若 `memberLevel` 缺失 -> `MEMBER_INFO_REQUIRED`。
        - 若 `memberLevel` 不在允许列表中 -> `MEMBER_LEVEL_MISMATCH`。
4.  **渠道发布校验 (Channel Publishing)**：
    - 校验该房型+价格计划是否已通过「渠道发布」功能发布至当前渠道（查询 `channel_publish_records`）。
    - 若未发布 -> `RATE_PLAN_NOT_PUBLISHED`。
5.  **库存扣减服务核心逻辑 (InventoryDeductionService)**：
    - **房态锁定 (Room Status)**：检查 `room_status` 表，若存在任一天 `is_open = false` -> `ROOM_CLOSED`。
    - **提前期校验 (Advance Booking)**：校验 `checkInDate - today` 是否满足 `advance_booking_days` -> `ADVANCE_BOOKING_VIOLATION`。
    - **入住周期校验 (Stay Duration)**：校验 `nights` 是否符合 `min_stay` 和 `max_stay` 限制 -> `STAY_DURATION_VIOLATION`。
    - **物理库存平衡 (Inventory Balance)**：检查 `inventory.available_rooms`（日期内最小值）是否 `>= roomCount` -> `INSUFFICIENT_INVENTORY`。
5.  **入住能力限制**：
    - 校验 `adultCount + childCount` 是否超过房型的 `max_occupancy`（默认 2）-> `EXCEED_MAX_OCCUPANCY`。
6.  **价格完整性审查**：
    - 校验日期范围内每一天在 `hotel_prices` 表中是否都有有效的 `price_with_tax`。
    - 有效价格定义：`status = active` 且 `price_with_tax > 0`。
    - 若存在空缺、失效价或 `0` 价 -> `PRICE_NOT_SET`。

2.  **核心业务校验 (串行执行)**：
    - **对象状态校验**：酒店、房型、价格计划必须存在且 `status` 为 `active`。
    - **渠道授权校验**：当前渠道必须在 `channel_hotel_mappings` 中有针对该酒店的 `active` 授权。
    - **渠道发布校验**：该房型+价格计划必须已发布至当前渠道（`channel_publish_records` 记录存在）。
    - **房型适用性**：若价格计划指定了房型列表，当前房型必须在其中。
    - **会员等级校验**：若价格计划有等级限制，请求必须携带匹配的 `memberLevel`。
3.  **可订性终审 (InventoryDeductionService)**：
    - 房态锁定：检查 `room_status` 日期记录。
    - 预订规则：校验提前预订天数、最少/最多入住晚数。
    - 库存余额：实时检查 `inventory.available_rooms` 是否足以支撑 `roomCount`。
4.  **入住人数硬限制**：
    - 校验 `adultCount + childCount` 是否超过房型的 `max_occupancy`（若房型未设置，默认上限为 2）。
5.  **价格完整性与一致性校验 (Double Check)**：
    - **价格日历断层拦截**：系统将查询数据库 `hotel_prices`，若发现入住期间存在任意一天没有设置价格，立即阻断并返回 `409 PRICE_NOT_SET`。
    - **明细对账**：系统必须遍历请求中的 `dailyPrices`。若请求传入的当日价格与数据库实时有效价格不一致（若酒店配置了最低价，则先按最低价抬升后再比对，误差 > 0.01），返回 `PRICE_MISMATCH`。
    - **总价对账**：校验 `SUM(dailyPrices[].price) * roomCount` 是否等于请求中的 `totalPrice`。若不一致，返回 `PRICE_MISMATCH`。
    - **实时抓取**：若请求未传明细（不建议），系统以数据库实时价格为准计算；若酒店配置了最低价，则按最低价抬升后再计算。
6.  **政策快照继承**：
    - 订单创建时，系统会根据当前价格计划关联的代码，从政策库中抓取最新的规则描述并持久化到订单镜像中。
7.  **订单号生成算法**：`CRS + yyyyMMdd + 6位递增序列`。
8.  **库存锁定**：在订单写入事务内执行 `inventory` 表扣减，失败则回滚订单。
9.  **入住人与房间映射规则 (Room-Guest Mapping)**：
    - `roomCount > 1` 时，建议 `guests` 列表至少包含与房间数相等的记录，以便系统为每间房分配首位入住人。若不足，系统将默认使用联系人信息填充缺失房间。
10. **支付期限与自动取消 (Payment Logic)**：
    - **预付订单 (Prepaid)**：若价格计划关联的担保政策类型为 `prepaid`，还需结合渠道配置 `prepaidOrderRequiresPayment` 判断。
      - 当渠道配置为 `true` 时：订单初始状态设为 `pending_payment`，系统会自动计算 30 分钟后的 `paymentDeadline`
      - 当渠道配置为 `false` 时：订单初始状态直接设为 `confirmed`，不生成 `paymentDeadline`
    - 担保政策类型字段 `guarantee_policies.type` 统一存储规则编码，不存储中文文案；历史中文值在过渡期需兼容识别，但新保存的数据必须归一化为编码。
    - **担保类型一致性**：订单返回字段 `guaranteeType` 表示该订单实际适用的担保政策类型，来源于价格计划绑定的担保政策，而不是请求体 `guaranteeInfo.type`。若请求体显式传入 `guaranteeInfo.type` 或 `guaranteeType`，其值必须与担保政策类型一致，否则返回 400。
    - **超时取消**：若在 `paymentDeadline` 之前未完成支付接口调用，系统定时任务将自动关闭订单（状态变为 `cancelled`，理由为 `PAYMENT_TIMEOUT`），并释放已锁定库存。
    - **现付订单 (Postpaid)**：直接进入 `confirmed` 状态。

### 接口 6：取消订单

渠道取消自己创建的订单。

- **方法**：`POST`
- **路径**：`/api/open/reservations/{reservationCode}/cancel`
- **状态**：✅ 已实现

#### 路径参数

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| reservationCode | String | 是 | CRS预订号 |

#### 请求体（可选）

```json
{
  "cancelReason": "客人行程变更"
}
```

#### 请求字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| cancelReason | String | 否 | 取消原因 |

#### 业务规则

1.  **前置身份校验**：仅允许订单所属渠道（`channel_id` 匹配）发起取消请求，否则返回 403。
2.  **订单状态限制**：仅 `confirmed`（已确认）和 `pending_payment`（待支付）状态的订单可执行取消。若订单已入住（`checked_in`）或已完成（`completed`），禁止取消。
3.  **取消规则核验 (Cancellation Policy Check)**：
    - 需先读取渠道配置 `cancelOrderChecksCancellationRule`。
    - 当该配置为 `true` 时：
      - 系统会查询订单镜像中的取消政策。
      - 取消政策类型判断需先做归一化，兼容历史中文值（如“不可取消”“提前取消”“限时扣费”）。
      - 若政策为 `non_refundable`（不可退），拒绝取消。
      - 若政策为 `limited`（限时取消），校验当前时间是否已超过免费取消截止日期。若已超时，返回 `CANCELLATION_FEE_REQUIRED` 并告知需扣除的金额。
    - 当该配置为 `false` 时：跳过取消政策校验，直接执行取消。
4.  **库存回滚与审计**：
    - 取消成功后，系统自动释放 `inventory` 占用的库存。
    - 记录操作历史及取消原因。

## 三、安全与性能要求

### 安全要求

1. **传输安全**：所有接口必须使用 HTTPS
2. **认证机制**：通过 `X-Api-Key` + `X-Api-Secret` 双重校验，对应 `tenant_channels` 表
3. **数据隔离**：所有查询和操作严格按 `tenant_id` 隔离
4. **渠道授权**：酒店数据仅对已通过 `channel_hotel_mappings` 授权的渠道可见
5. **敏感数据**：信用卡信息需加密传输和存储
6. **频率限制**：单渠道每秒最大请求数 100
7. **审计日志**：系统必须完整记录所有开放 API 的请求（URL, Method, Headers, Body）与响应（Status, Body, Duration），并能追踪到具体的调用渠道。所有 4xx 和 5xx 错误必须保留异常堆栈以便排障。

### 性能要求

| 接口 | 目标响应时间 |
|------|-------------|
| 查询酒店列表 | ≤ 500ms |
| 查询酒店详情与价格 | ≤ 800ms |
| 可订检查 | ≤ 300ms |
| 创建订单 | ≤ 1000ms |
| 支付订单 | ≤ 500ms |
