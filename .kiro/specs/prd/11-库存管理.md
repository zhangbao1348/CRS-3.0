# 库存管理

库存管理是 CRS 系统的酒店端库存控制模块，负责酒店房间库存的日历化管理、房态控制和预订规则配置。库存管理的数据以当前选中的酒店为上下文。

库存管理包含以下菜单：房控日历、房态管理、预订控制。

---

## 1. 房控日历

### 1.1 主要房控日历 ✅ 已实现

房控日历以横向滚动表格形式展示各房型在各日期的库存、房价和开关房状态，数据来源于后端API。

页面顶部有以下筛选控件：
- **库存类型切换**：下拉选择，固定选项：库存/房价/开关房（3种视图模式）
- **房型筛选**：下拉选择，"全部房型"或具体房型（从当前酒店房型列表获取，显示"名称（代码）"格式）
- **价格计划筛选**：仅在"房价"模式下显示，"全部价格计划"或具体价格计划（从当前酒店价格计划列表获取）
- **筛选按钮**和**刷新按钮**

表格结构：
- 表头左上角有上月/下月切换按钮和当前月份显示
- 左侧固定列：房型名称（按行数合并）+ 子类型列
- 右侧日期列：当月每天一列，表头显示月.日和星期，周末浅黄色背景

**库存类型=库存时：** 数据来源于 PMS 库存（GET /api/pms-inventory）。每个房型展示两行：
- 可售（蓝色）：剩余可售房间数
- 已售（黄色）：已售数量（后端计算）
- 单元格可点击编辑可售数量

**库存类型=房价时：** 数据来源于酒店价格（GET /api/hotel-prices/query）。每个房型按价格计划展示多行，每行显示该价格计划在各日期的价格（¥xxx）。单元格可点击编辑房价，通过 POST /api/hotel-prices 保存。

**库存类型=开关房时：** 数据来源于房态（GET /api/room-status）和 PMS 库存。每个房型展示三行：
- 可售（蓝色）：来自PMS库存的可售数
- 已售（黄色）：来自PMS库存的已售数
- 房态（绿色）：显示"开"（绿色背景）或"关"（红色背景），点击直接切换，通过 POST /api/room-status 保存。无记录时默认"开"。

### 1.2 PMS 房控日历 ✅ 已实现

PMS 房控日历展示从 PMS 系统同步过来的库存数据，以横向滚动表格形式按房型展示每日库存明细。

页面顶部有房型筛选下拉（"全部房型"或具体房型，显示"名称（代码）"格式）、筛选按钮和查看同步日志按钮。

表格结构：
- 左侧固定列：房型名称（每 5 行合并为一组）+ 库存类型
- 右侧日期列：每天一列，表头显示日期和星期，周末浅黄色背景
- 每个房型下展示 5 行：
  - **物理房型数**（蓝色）：该房型的总房间数，由PMS同步
  - **已售**（绿色）：= 物理房型数 + 超预订数 - 剩余可售 - 维修房数，前端由后端计算返回
  - **维修**（黄色）：维修房数量，由PMS同步。无维修房时显示"-"
  - **超预订**（红色）：超预订数量，由PMS同步。无超预订时显示"-"
  - **可售**（青色）：剩余可售房数，由PMS同步
- 表头有上月/下月切换按钮
- 无数据时显示"-"（灰色）

PMS 房控日历为只读展示，不支持编辑操作。数据由 PMS 系统通过同步接口写入。

同步日志弹窗展示 PMS 同步记录，包含同步时间、同步类型（全量/增量）、状态（成功/失败）、详情。

**数据存储：** PMS 库存数据存储在 `pms_inventory` 表中，每条记录对应一个房型在一个日期的库存数据。字段包括：
- `physical_rooms`：物理房型数（总房间数）
- `available_rooms`：剩余可售房数
- `maintenance_rooms`：维修房数
- `overbook_count`：超预订数
- 已售数量通过公式计算：已售 = 物理房型数 + 超预订数 - 剩余可售 - 维修房数

唯一约束：tenant_id + hotel_code + room_type_code + inventory_date

同步日志存储在 `pms_sync_logs` 表中。

**API 接口：**
- GET /api/pms-inventory：查询PMS库存数据（支持按房型筛选）
- POST /api/pms-inventory：保存单条PMS库存数据（供PMS同步调用）
- POST /api/pms-inventory/batch：批量保存PMS库存数据（供PMS同步调用）
- GET /api/pms-inventory/sync-logs：查询PMS同步日志

### 1.3 酒店超预订管理 ✅ 已实现

酒店级别的超预订配置，以月度日历形式展示和编辑每个日期的超预订数量。

日历以标准月历形式展示，每个日期格子显示"超预订: X"。点击日期格子弹出编辑弹窗修改超预订数量。支持批量修改（选择日期范围 + 超预订数量）。

超预订数量表示在该日期允许超出实际房间数量的预订数。比如酒店有 100 间房，超预订设为 5，则最多可接受 105 个预订。默认超预订数量为 0（不允许超预订）。

数据存储在 `overbooking` 表中，dimension_type='hotel'。

### 1.4 房型超预订管理 ✅ 已实现

房型级别的超预订配置，以横向滚动表格形式展示所有房型在各日期的超预订数量。

页面顶部有房型筛选下拉（"全部房型"或具体房型，显示"名称（代码）"格式）、批量修改按钮和日志按钮。

表格结构：
- 左侧固定列：房型名称（代码），每个房型一行
- 右侧日期列：每天一列，表头显示日期和星期，过去日期灰色背景
- 每个单元格显示该房型在该日期的超预订数量，点击可编辑（过去日期不可点击）
- 表头有上月/下月切换按钮

批量修改弹窗支持多选房型 + 日期范围 + 超预订数量，一次性为多个房型设置。

数据存储在 `overbooking` 表中，dimension_type='room_type'，dimension_code=房型CODE。

酒店超预订和房型超预订都有操作日志功能，日志记录操作人、操作时间、操作类型（单个/批量）、操作明细（旧值→新值 或 日期范围+设置值）。日志弹窗中包含"房型"列，显示该条日志对应的房型名称（通过 dimensionCode 匹配房型列表）。当筛选为"全部"时，日志查询返回该 dimensionType 下所有维度项的日志。日志数据存储在 `overbooking_logs` 表中。

### 1.5 房价级房量管理 ✅ 已实现

按价格计划维度管理房间库存分配，以横向滚动表格形式展示。

页面顶部有房价码筛选下拉（"全部价格"或具体房价码，显示"名称（代码）"格式）、批量修改按钮和日志按钮。

表格结构：
- 左侧固定列：房价码名称（每 3 行合并为一组）+ 库存类型（已售/剩余可售/库存限制）
- 右侧日期列：每天一列，表头显示日期和星期，过去日期灰色背景
- 每个房价码下展示 3 行：
  - **已售**（蓝色）：已售数量，由订单系统更新
  - **剩余可售**（绿色）：= 库存限制 - 已售，实时计算。未设置限制时显示"-"
  - **库存限制**（黄色）：可点击编辑的库存限制数量，未设置显示"-"
- 只有"库存限制"行的单元格可点击编辑（过去日期不可点击）
- 表头有上月/下月切换按钮

批量修改弹窗支持多选房价码 + 日期范围 + 库存限制数量。

### 1.6 渠道级房量管理 ✅ 已实现

按渠道维度管理房间库存分配。页面顶部选择渠道（从三级渠道码获取，显示"名称（代码）"），表格结构与房价级一致，每个渠道下 3 行（已售/剩余可售/库存限制）。

### 1.7 市场码级房量管理 ✅ 已实现

按市场码维度管理房间库存分配。页面顶部选择市场码（从三级市场码获取），表格结构与房价级一致。

### 1.8 渠道+房型级房量 ✅ 已实现

按渠道和房型的交叉维度管理房间库存分配。页面顶部有两个独立的筛选下拉：渠道筛选（"全部渠道"或具体渠道）和房型筛选（"全部房型"或具体房型），用户可分别选择渠道和房型进行过滤。dimension_code 格式为"渠道CODE:房型CODE"。表格结构与房价级一致，展示筛选后的渠道×房型交叉组合。

### 1.9 房价大类房量控制 ✅ 已实现

按房价大类维度管理房间库存分配。页面顶部选择房价大类，表格结构与房价级一致。

**房量控制数据存储：** 所有 5 个维度的房量数据存储在同一张 `inventory_quota` 表中，通过 `dimension_type` 区分。表中有两个核心字段：
- `quota_limit`：库存限制（NULL 表示未设置，不限制）
- `sold_count`：已售数量（由订单系统在创建/支付订单时更新，默认 0）

剩余可售 = quota_limit - sold_count，前端实时计算显示。

操作日志存储在 `inventory_quota_logs` 表中，记录操作人、操作时间、操作类型、变更明细。日志弹窗中包含维度项列（如"房价码"、"渠道"等），显示该条日志对应的维度项名称（通过 dimensionCode 匹配维度项列表）。当筛选为"全部"时，日志查询返回该 dimensionType 下所有维度项的日志；当筛选为具体维度项时，只返回该维度项的日志。

## 2. 房态管理

房态管理用于控制酒店在各维度下每个日期的"开房/关房"状态。页面采用统一的 Tab 切换设计，7 个维度共用一个组件，数据存储在同一张 `room_status` 表中，通过 `dimension_type` 和 `dimension_code` 区分维度。

**默认行为：** 当某个日期没有记录时，默认显示"开"（绿色），表示默认开房状态。只有明确设置为关房的日期才会显示"关"（红色）。

房态管理支持 7 个维度，通过页面顶部的 Tab 切换：

| Tab | dimension_type | 说明 | 筛选条件 |
|-----|---------------|------|---------|
| 酒店级房态 | hotel | 酒店整体的开关房状态 | 无（直接显示当前酒店的日历） |
| 房型级房态 | room_type | 按房型控制开关房 | 需先选择房型 |
| 房价级房态 | rate | 按价格计划控制开关房 | 需先选择房价码 |
| 渠道级房态 | channel | 按渠道控制开关房 | 需先选择渠道 |
| 渠道+房型级房态 | channel_room_type | 按渠道和房型交叉维度控制 | 需先选择渠道和房型，dimension_code 格式为"渠道CODE:房型CODE" |
| 市场码级房态 | market | 按市场码控制开关房 | 需先选择市场码 |
| 房价大类房态 | rate_category | 按房价大类控制开关房 | 需先选择房价大类 |

### 2.1 房态日历 ✅ 已实现（前后端已对接）

每个 Tab 下展示一个月度日历网格。日历以标准月历形式展示（7列代表周日到周六），每个日期格子里显示当天的房态状态：

- **开**（绿色文字）：该日期开房（默认状态，无记录时也显示开）
- **关**（红色文字）：该日期已关房（需明确设置）

周末日期（周六、周日）格子有浅黄色背景。

日历上方有月份切换按钮（上月/下月）、"批量开房"按钮（绿色）和"批量关房"按钮（红色）。

**单个日期切换：** 点击某个日期格子，立即切换该日期的开/关状态（无需弹窗确认），保存后即时更新显示。过去的日期不可点击（半透明显示，鼠标变为禁止图标）。

**日期修改限制：** 以**酒店当地时间 (Hotel Local Time) 06:00:00** 为系统日切边界。每天当地时间 6 点之前可以修改昨天及今天以后的房态，6 点之后只能修改今天及以后的房态。更早的历史日期数据强制锁定不可修改。批量修改的日期范围选择器也遵循此限制。

**批量修改：** 点击"批量修改"按钮，弹出弹窗，先选择"开房"或"关房"（Radio 单选），再选择日期范围，确认后将选中日期范围内的所有日期统一设置。在"渠道+房型级房态"Tab 下，批量弹窗中额外显示房型多选下拉，支持一次性选择多个房型。

### 2.2 房态操作日志 ✅ 已实现

每个 Tab 的批量修改按钮旁边有"日志"按钮，点击后弹出操作日志弹窗。

日志记录以下信息：

| 列 | 说明 |
|----|------|
| 操作时间 | 精确到秒 |
| 操作人 | 执行操作的用户名 |
| 操作类型 | 单个修改（绿色标签）/ 批量修改（蓝色标签） |
| 操作明细 | 单个修改显示"日期：旧值 → 新值"；批量修改显示"日期范围 + 开房/关房" |

日志按操作时间倒序排列，每页 10 条。

**各 Tab 下拉数据来源：**
- 房型 Tab：从当前酒店的房型列表获取，显示"名称（代码）"
- 房价码 Tab：从当前酒店的价格计划列表获取，显示"名称（代码）"
- 渠道 Tab：从三级渠道码 API 获取，显示"名称（代码）"
- 渠道+房型 Tab：需同时选择渠道和房型两个下拉
- 市场码 Tab：从三级市场码 API 获取，显示"名称（代码）"
- 房价大类 Tab：从房价大类 API 获取，显示"名称（代码）"

### 2.3 数据存储设计 ✅ 已实现

所有维度的房态数据存储在同一张表 `room_status` 中，通过 `dimension_type` 和 `dimension_code` 区分不同维度。

**为什么用一张表而不是 7 张表？**
- 7 个维度的数据结构完全一致（都只有一个 `is_open` 字段）
- 一张表方便统一查询和维护，避免重复的 CRUD 代码
- 与 `booking_controls` 表采用相同的设计模式

**表结构：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT | 主键 |
| tenant_id | INT | 租户ID |
| hotel_code | VARCHAR(50) | 酒店CODE |
| dimension_type | VARCHAR(30) | 维度类型：hotel / room_type / rate / channel / channel_room_type / market / rate_category |
| dimension_code | VARCHAR(100) | 维度值：酒店维度为空，其他维度为对应的 CODE |
| status_date | DATE | 日期 |
| is_open | TINYINT(1) | 0=关, 1=开，默认0 |
| created_at | TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMP | 更新时间 |

**唯一约束：** tenant_id + hotel_code + dimension_type + dimension_code + status_date 的组合不可重复。

**API 接口：**
- GET /api/room-status：查询指定维度和日期范围的房态数据
- POST /api/room-status：单个日期的开关房保存（upsert）
- POST /api/room-status/batch：批量日期的开关房保存

## 3. 预订控制

预订控制用来管理"客人在什么条件下可以预订"。比如某个日期要求提前 3 天预订、最少住 2 晚、取消规则是"限时取消"等。

预订控制支持 5 个维度，通过页面顶部的 Tab 切换：

| Tab | 维度 | 说明 | 筛选条件 |
|-----|------|------|---------|
| 酒店预订控制 | hotel | 酒店整体的预订规则，对所有房型和渠道生效 | 无（直接显示当前酒店的日历） |
| 房价预订控制 | rate | 按房价码设置预订规则，比如"会员价要求提前7天预订" | 需先选择房价码 |
| 渠道预订控制 | channel | 按渠道设置预订规则，比如"携程渠道最少住2晚" | 需先选择渠道 |
| 房价大类预订控制 | rate_category | 按房价大类设置预订规则 | 需先选择房价大类 |
| 市场预订控制 | market | 按市场码设置预订规则 | 需先选择市场码 |

### 3.1 预订控制日历 ✅ 已实现

每个 Tab 下展示一个月度日历网格。日历以标准月历形式展示（7列代表周日到周六），每个日期格子里显示当天的预订控制规则摘要：

- **取消规则**（蓝色）：显示具体的取消政策名称（如：不可取消/限时扣费等）
- **提前预订天数**（绿色）：提前 X 天
- **连住天数**（黄色）：X-Y 晚

日历上方有月份切换按钮（上月/下月）和"批量修改"按钮。

**单个日期修改：** 点击某个日期格子，弹出编辑弹窗，可修改该日期的 4 个预订控制字段：
- 取消规则（下拉选择，数据来源于集团取消政策管理，显示格式为"名称（代码）"）
- 提前预订天数（数字输入，最小 0）
- 最小连住天数（数字输入，最小 1）
- 最大连住天数（数字输入，最小 1）

**批量修改：** 点击"批量修改"按钮，弹出弹窗，先选择日期范围，再设置 4 个预订控制字段（取消规则同样从集团取消政策获取），确认后批量更新选中日期范围内的所有日期。

**日历格子中的取消规则显示：** 显示为"名称（代码）"格式，与编辑弹窗中的下拉选项一致。

**各 Tab 下拉数据来源：**
- 房价码 Tab：从当前酒店的价格计划列表获取，显示"名称（代码）"
- 渠道 Tab：从三级渠道码 API 获取，显示"名称（代码）"
- 房价大类 Tab：从房价大类 API 获取，显示"名称（代码）"
- 市场码 Tab：从三级市场码 API 获取，显示"名称（代码）"

### 3.2 预订控制操作日志 ✅ 已实现

每个 Tab 的批量修改按钮旁边有"日志"按钮，点击后弹出操作日志弹窗，展示当前维度下的预订控制变更记录。

日志记录以下信息：

| 列 | 说明 |
|----|------|
| 操作时间 | 精确到秒 |
| 操作人 | 执行操作的用户名 |
| 操作类型 | 单个修改（绿色标签）/ 批量修改（蓝色标签） |
| 操作明细 | 单个修改显示"日期 + 每个字段的旧值→新值"；批量修改显示"日期范围 + 设置的值" |

日志按操作时间倒序排列，每页 10 条。日志数据存储在 booking_control_logs 表中，每次保存时自动记录。

**举例：**
- 酒店管理员打开"酒店预订控制"Tab，看到 2026 年 5 月的日历
- 点击 5 月 1 日的格子，弹窗中把取消规则改为"不可取消"，提前预订天数改为 7，保存
- 然后点击"批量修改"，选择 5 月 1 日到 5 月 7 日，设置最小连住 2 晚、最大连住 7 晚，保存
- 切换到"渠道预订控制"Tab，选择"携程"，给携程渠道单独设置 5 月份的预订规则

### 3.3 数据存储设计

所有维度的预订控制数据存储在同一张表 `booking_controls` 中，通过 `dimension_type` 和 `dimension_code` 区分不同维度。

**为什么用一张表而不是 5 张表？**
- 5 个维度的数据结构完全一致（都是 4 个字段：取消规则、提前天数、最小连住、最大连住）
- 一张表方便统一查询和维护，避免重复的 CRUD 代码
- 通过 `dimension_type` 字段区分维度，查询时加上维度条件即可

**表结构：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT | 主键 |
| tenant_id | INT | 租户ID |
| hotel_code | VARCHAR(50) | 酒店CODE |
| dimension_type | VARCHAR(20) | 维度类型：hotel / rate / channel / rate_category / market |
| dimension_code | VARCHAR(50) | 维度值：酒店维度为空，其他维度为对应的 CODE（如房价码 CODE、渠道 CODE 等） |
| control_date | DATE | 日期 |
| cancellation_policy_code | VARCHAR(50) | 取消政策代码（动态关联集团取消政策，如 CANCEL_001） |
| advance_booking_days | INT | 提前预订天数 |
| min_stay | INT | 最小连住天数 |
| max_stay | INT | 最大连住天数 |
| created_at | TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMP | 更新时间 |

**唯一约束：** tenant_id + hotel_code + dimension_type + dimension_code + control_date 的组合不可重复。

**查询示例：**
- 查酒店级 5 月预订控制：`WHERE hotel_code='JJSH001' AND dimension_type='hotel' AND control_date BETWEEN '2026-05-01' AND '2026-05-31'`
- 查携程渠道 5 月预订控制：`WHERE hotel_code='JJSH001' AND dimension_type='channel' AND dimension_code='CTRIP' AND control_date BETWEEN ...`

## 库存管理的层级关系

CRS 系统的库存管理采用多层级控制体系，从粗到细依次为：

1. **酒店级**：控制酒店整体的库存和房态
2. **房型级**：在酒店级基础上，按房型细分控制
3. **房价级/房价大类级**：按价格计划或房价大类维度控制
4. **渠道级**：按销售渠道维度控制
5. **渠道+房型级**：最细粒度，按渠道和房型的交叉维度控制
6. **市场码级**：按市场码维度控制

各层级的控制相互独立，当多个层级的规则同时生效时，系统按以下**冲突解决策略**进行合并运算（详细时序见《订单核心逻辑.md》）：

1. **房态 (Room Status)**：取各层级的交集，即所有相关维度都为"开"时，最终房态才为"开"。
2. **库存配额 (Inventory Quota)**：最终可用库存取【各维度剩余库存限制】与【PMS 物理可售房量】中的**最小值 (Min)**。
3. **预订控制 (Booking Controls)**：
   - **提前预订天数**：取所有生效维度中的**最大值**（最严标准）。
   - **最小连住天数**：取所有生效维度中的**最大值**（最严标准）。
   - **最大连住天数**：取所有生效维度中的**最小值**（最严标准）。
   - **取消政策**：取所有生效维度中限制最严的政策（如：不可取消 > 限时扣费 > 免费取消）。
