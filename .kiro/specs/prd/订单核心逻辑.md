# 订单核心逻辑 —— 库存扣减

本文档定义 CRS 系统订单核心逻辑中关于库存扣减的完整规则，分为**业务规则**和**技术设计**两部分。

---

# 第一部分：业务规则

---

## 1. 库存体系概述

### 1.1 两大库存体系

CRS 系统的库存由两大体系共同管理，订单核心逻辑必须同时操作两套体系，确保数据一致：

**物理库存体系**：记录酒店每种房型每天的实际房间情况，包括物理总房量、可售量、维修量和超预订量。数据来源于 PMS 系统同步和酒店管理员手动维护。物理库存是基础约束，但在超预订机制下可以突破。

**多维度配额体系**：在物理库存的基础上，按不同业务维度（房价码、渠道、市场码等）设置配额上限和已售数量。配额是"软上限"——用于控制各维度的销售分配，防止某个维度占用过多库存。配额未设置时表示不限制，设置了上限后则受上限约束。

**超预订机制**：允许在特定条件下突破物理库存限制进行售卖。超预订分为两个层级——房型级和酒店级，两者存在上下级约束关系（详见第 2.9 节）。

**三者关系**：物理库存是基础，超预订机制是物理库存的突破条件，配额体系是叠加控制。实际可售数综合考虑三者，取各层级可售数的最小值。

### 1.2 辅助控制机制

除两大库存体系外，还有以下辅助控制机制影响可售性：

- **房态控制**：按酒店、房型、房价码、渠道、市场码等 7 种维度控制每天的开关房状态。关房 = 该维度当天不可售。
- **预订规则控制**：按酒店、房价码、渠道、市场码、房价大类等 5 种维度设置提前预订天数、最小/最大连住天数等规则。
- **超预订设置**：允许酒店级或房型级别的超额预订。房型级超预订允许该房型售卖超过其物理剩余库存，但仍受酒店整体剩余库存约束；酒店级超预订则允许整个酒店维度超卖。两者形成层级约束关系。

### 1.3 废弃旧版库存体系

系统早期存在一套独立的库存体系（旧版库存），该体系与上述两大体系并行但数据不一致——订单扣减只更新旧版库存，配额体系的已售数据从未被更新。本方案将废弃旧版库存体系，所有库存操作统一迁移至物理库存 + 配额体系。

## 2. 库存可售性检查

### 2.1 核心原则

**实际可售数 = 各层级可售数的最小值**

一个预订请求是否可售，需要综合所有层级的库存数据，取最小值作为最终可售数。如果任一层级可售数不足，则不可售。

### 2.2 检查层级

按优先级从高到低，依次执行以下 8 个层级的检查：

| 层级 | 检查内容 | 判断方式 |
|------|----------|----------|
| 层级1 | 房态检查 | 任一维度关房 → 直接拒绝 |
| 层级2 | 预订规则检查 | 不满足规则 → 拒绝 |
| 层级3 | 物理库存 | 可售量 < 请求量 → 拒绝 |
| 层级4 | 房价码配额 | 剩余配额 < 请求量 → 拒绝 |
| 层级5 | 渠道配额 | 剩余配额 < 请求量 → 拒绝 |
| 层级6 | 市场码配额 | 剩余配额 < 请求量 → 拒绝 |
| 层级7 | 渠道+房型交叉配额 | 剩余配额 < 请求量 → 拒绝 |
| 层级8 | 房价大类配额 | 剩余配额 < 请求量 → 拒绝 |

### 2.3 层级1：房态检查

**检查范围**：入住日期到离店前一天的每一天，每天检查 7 种维度的房态。

**7 种维度**（按优先级排列）：

1. **酒店级**：酒店整体是否关房
2. **房型级**：该房型是否关房
3. **房价码级**：该房价码是否关房
4. **房价大类级**：该房价大类是否关房
5. **渠道级**：该渠道是否关房
6. **渠道+房型级**：该渠道的该房型是否关房
7. **市场码级**：该市场码是否关房

**判断规则**：
- 未设置房态 = 默认开房（可售）
- 明确设置为关房 = 不可售
- 任一天任一维度关房 → 整个预订不可售

**维度与订单信息的对应关系**：
- 酒店级：适用于当前酒店
- 房型级：对应订单中的房型
- 房价码级：对应订单中的房价码
- 房价大类级：对应订单房价码所属的房价大类
- 渠道级：对应订单中的渠道
- 渠道+房型级：对应订单中的渠道和房型的组合
- 市场码级：对应订单中的市场码（如有）

### 2.4 层级2：预订规则检查

**检查范围**：入住期间的每一天，检查 5 种维度的预订规则，取最严格的规则。

**5 种维度**（按优先级排列）：

1. **酒店级**：酒店整体的预订规则
2. **房价码级**：该房价码的预订规则
3. **渠道级**：该渠道的预订规则
4. **房价大类级**：该房价大类的预订规则
5. **市场码级**：该市场码的预订规则

**检查项目**：

| 规则 | 判断逻辑 | 不满足时的提示 |
|------|----------|----------------|
| 提前预订天数 | 预订日期距当前日期的天数 ≥ 设定值 | "需提前 X 天预订" |
| 最小连住天数 | 入住天数 ≥ 设定值 | "最少需住 X 晚" |
| 最大连住天数 | 入住天数 ≤ 设定值 | "最多可住 X 晚" |

**规则合并策略**：当多个维度都设置了规则时，取最严格值：
- 提前预订天数 → 取最大值
- 最小连住天数 → 取最大值
- 最大连住天数 → 取最小值

**逐日检查**：入住期间的每一天都需要检查当天的预订规则，任一天不满足则拒绝。

### 2.5 层级3：物理库存检查（含超预订）

**数据来源**：PMS 系统同步的每日房型库存 + 超预订设置。

**查询维度**：酒店 + 房型 + 日期。

**核心规则：房型最终可售数 = min(房型可售数, 酒店可售数)**

所有房型（无论是否设置了超预订）的最终可售数，都需要与酒店可售数对比取最小值，确保不会突破酒店维度的物理库存上限。

#### 房型可售数计算

```
房型可售数 = 房型物理总房量 + 房型超预订量 - 已售数量 - 维修量
```

- 房型超预订量未设置（=0）时：房型可售数 = 物理总房量 - 已售 - 维修（不可超卖）
- 房型超预订量已设置（>0）时：房型可售数可以超过物理总房量。例如某房型有 10 间房，超预订设为 2，则最多可售 12 间

#### 酒店可售数计算

```
酒店可售数 = 所有房型原始可售数之和 + 酒店超预订量
```

其中：

```
房型原始可售数 = 房型物理总房量 - 已售数量 - 维修量（不含房型超预订量）
```

即酒店可售数 = 所有房型（物理总房量 - 已售 - 维修）之和 + 酒店超预订量。

- 酒店超预订量未设置（=0）时：酒店可售数 = 所有房型原始可售数之和（酒店不可超卖）
- 酒店超预订量已设置（>0）时：酒店可售数可以超过所有房型物理总房量之和

#### 最终可售数

```
房型最终可售数 = min(房型可售数, 酒店可售数)
```

**为什么所有房型都需要与酒店可售数对比？**

即使房型未设置超预订，其可售数也可能大于酒店可售数。例如：酒店有 A、B 两个房型，各 10 间。A 已售 8 间（可售 2 间），B 已售 0 间（可售 10 间）。酒店可售数 = 2 + 10 = 12。此时 B 的可售数（10）≤ 酒店可售数（12），不受约束。

但如果 A 设置了超预订 5 间且已售 13 间（可售 10+5-13=2 间），B 已售 0 间（可售 10 间），酒店可售数 = (10-13) + (10-0) = -3 + 10 = 7。此时 B 的可售数（10）> 酒店可售数（7），B 的最终可售数应为 7，避免突破酒店维度的可售上限。

**检查规则**：
- 逐日查询入住期间每天的可售量
- 每天最终可售数 ≥ 请求房间数 → 可售
- 无数据 = 0 间可售（拒绝）

### 2.6 层级4-8：多维度配额检查

**数据来源**：各维度的配额设置。

**可售数计算**：

```
配额可售数 = 配额上限 - 已售数量
```

- 配额上限未设置 → 不限制（该层级不参与取最小值，跳过）
- 配额上限已设置 → 配额可售数 = 配额上限 - 已售数量

**5 种配额维度**：

| 维度 | 对应订单信息 | 说明 |
|------|-------------|------|
| 房价码配额 | 订单的房价码 | 控制某个房价码最多可售多少间 |
| 渠道配额 | 订单的渠道 | 控制某个渠道最多可售多少间 |
| 市场码配额 | 订单的市场码（如有） | 控制某个市场码最多可售多少间 |
| 渠道+房型配额 | 订单的渠道 + 房型 | 控制某个渠道的某个房型最多可售多少间 |
| 房价大类配额 | 订单房价码所属的房价大类 | 控制某个房价大类最多可售多少间 |

**检查规则**：
- 逐日查询各维度的配额数据
- 配额可售数 ≥ 请求房间数 → 可售
- 配额上限未设置 → 跳过该维度

### 2.7 综合可售数计算

**逐日计算**：对入住期间的每一天，取所有层级可售数的最小值作为当日可售数。

**整体判断**：取所有天中可售数的最小值作为最终可售数。最终可售数 ≥ 请求房间数 → 可售。

### 2.8 可售性检查示例

**场景**：携程渠道预订 2026-05-10 至 2026-05-12（2晚），1间，房型 ST1，房价码 RACK

**5月10日各层级可售数**：

| 层级 | 数据 | 可售数 |
|------|------|--------|
| 房态 | 所有维度均开房 | 通过 |
| 预订规则 | 提前1天，最少1晚 | 通过 |
| 物理库存 | 可售5间 | 5 |
| 房价码配额 | 上限10，已售6 | 4 |
| 渠道配额 | 上限8，已售5 | 3 |
| 市场码配额 | 未设置上限 | 不限制 |
| 渠道+房型配额 | 未设置上限 | 不限制 |
| 房价大类配额 | 上限20，已售15 | 5 |

当日可售数 = min(5, 4, 3, 5) = **3**

**5月11日各层级可售数**：

| 层级 | 数据 | 可售数 |
|------|------|--------|
| 物理库存 | 可售3间 | 3 |
| 房价码配额 | 上限10，已售8 | 2 |
| 渠道配额 | 上限8，已售6 | 2 |
| 房价大类配额 | 上限20，已售16 | 4 |

当日可售数 = min(3, 2, 2, 4) = **2**

**最终可售数 = min(3, 2) = 2**，请求 1 间 → **可售** ✅

### 2.9 超预订专项示例

以下示例统一应用规则：**房型最终可售数 = min(房型可售数, 酒店可售数)**

#### 示例1：房型超预订 + 酒店未设超预订

**场景**：酒店有 A、B 两个房型。A 物理总房量 10 间，超预订量 2，已售 9 间，维修 0 间；B 物理总房量 40 间，已售 39 间，维修 2 间。酒店超预订量 = 0。请求预订 A 房型 2 间。

**计算过程**：
- A 房型可售数 = 10 + 2 - 9 - 0 = **3**（房型允许超卖）
- A 房型原始可售数 = 10 - 9 - 0 = **1**（不含超预订）
- B 房型原始可售数 = 40 - 39 - 2 = **-1**（已超卖）
- 酒店可售数 = 1 + (-1) + 0 = **0**（酒店不允许超卖，整体已无剩余）
- A 房型最终可售数 = min(3, 0) = **0** → **不可售** ❌

**结论**：虽然 A 房型设置了超预订允许卖 12 间，但酒店整体已无剩余且不允许超卖，因此不可售。

#### 示例2：房型超预订 + 酒店也设超预订

**场景**：酒店有 A、B 两个房型。A 物理总房量 10 间，超预订量 2，已售 9 间，维修 0 间；B 物理总房量 40 间，已售 39 间，维修 2 间。酒店超预订量 = 5。请求预订 A 房型 2 间。

**计算过程**：
- A 房型可售数 = 10 + 2 - 9 - 0 = **3**
- A 房型原始可售数 = 10 - 9 - 0 = **1**
- B 房型原始可售数 = 40 - 39 - 2 = **-1**
- 酒店可售数 = 1 + (-1) + 5 = **5**（酒店允许超卖）
- A 房型最终可售数 = min(3, 5) = **3** → 请求 2 间 → **可售** ✅

**结论**：房型和酒店都设置了超预订，房型可按自身超预订量售卖，酒店可售数（5）> 房型可售数（3），不受酒店约束。

#### 示例3：房型未设超预订 + 酒店设超预订

**场景**：房型 ST1 物理总房量 10 间，超预订量 = 0，已售 10 间，维修 0 间。酒店超预订量 = 5。请求预订 1 间。

**计算过程**：
- ST1 房型可售数 = 10 + 0 - 10 - 0 = **0**（房型未设超预订，不可超卖）
- ST1 房型原始可售数 = 10 - 10 - 0 = **0**
- 酒店可售数 = 0 + 其他房型原始可售数 + 5（取决于其他房型情况）
- ST1 房型最终可售数 = min(0, 酒店可售数) = **0** → **不可售** ❌

**结论**：即使酒店允许超卖，房型自身未设超预订也不能超卖。超预订的生效前提是房型自身设置了超预订量。

#### 示例4：其他房型超卖导致酒店可售数下降

**场景**：酒店有 A、B 两个房型，各 10 间。A 超预订量 5，已售 13 间；B 未设超预订，已售 0 间，维修 0 间。酒店超预订量 = 0。请求预订 B 房型 10 间。

**计算过程**：
- B 房型可售数 = 10 + 0 - 0 - 0 = **10**
- A 房型原始可售数 = 10 - 13 - 0 = **-3**（A 已超卖）
- B 房型原始可售数 = 10 - 0 - 0 = **10**
- 酒店可售数 = (-3) + 10 + 0 = **7**
- B 房型最终可售数 = min(10, 7) = **7** → 请求 10 间 → **不可售** ❌（仅可售 7 间）

**结论**：虽然 B 房型自身有 10 间可售，但 A 房型超卖导致酒店整体可售数下降为 7，B 房型最终只能售 7 间，避免突破酒店维度的物理库存上限。

## 3. 创建订单时的库存扣减

### 3.1 扣减原则

创建订单时，需要**同时更新所有相关层级的库存数据**，确保各层级已售数据一致。任一层级扣减失败，所有已扣减的库存必须恢复原状。

### 3.2 扣减流程

```
创建订单 → 可售性检查通过 → 扣减库存 → 保存订单
                                    ↓
                        ┌───────────────────────────┐
                        │ 1. 扣减物理库存（减少可售量）│
                        │ 2. 扣减房价码配额（增加已售）│
                        │ 3. 扣减渠道配额（增加已售）  │
                        │ 4. 扣减市场码配额（增加已售）│
                        │ 5. 扣减渠道+房型配额（增加已售）│
                        │ 6. 扣减房价大类配额（增加已售）│
                        └───────────────────────────┘
```

### 3.3 各层级扣减规则

#### 物理库存扣减

- **操作**：减少可售量
- **防超卖**：扣减前检查可售量是否充足，不足则拒绝
- **超预订场景**：当房型设置了超预订且可售性检查已通过时，可售量可能为负数（表示已超卖），此时仍允许扣减。扣减时需同时校验房型可售数和酒店可售数，确保不超过 min(房型可售数, 酒店可售数)
- **逐日执行**：入住期间每天都要扣减
- **扣减后数据变化**：可售量减少，已售数量增加，物理总房量和维修量不变

#### 各维度配额扣减

- **操作**：增加已售数量
- **防超额**：扣减前检查剩余配额是否充足，不足则拒绝
- **逐日执行**：入住期间每天都要扣减
- **跳过规则**：如果该日期该维度没有设置配额上限，则跳过（不限制 = 不扣减）
- **条件执行**：
  - 市场码配额：仅当订单有市场码时执行
  - 房价大类配额：仅当房价码关联了房价大类时执行

### 3.4 扣减顺序

```
1. 物理库存（最基础，必须先扣减成功）
2. 房价码配额
3. 渠道配额
4. 市场码配额（如有）
5. 渠道+房型配额
6. 房价大类配额（如有）
```

**失败回滚**：任一层级扣减失败，所有已扣减的库存自动恢复。

### 3.5 扣减示例

**订单信息**：酒店 JJSH001，房型 ST1，房价码 RACK，渠道 CTRIP，市场码 LEISURE，入住 2026-05-10 至 2026-05-12，1间

**5月10日扣减结果**：

| 层级 | 扣减前 | 扣减后 |

## 4. 取消订单时的库存返还

### 4.1 返还原则

取消订单时，需要**返还所有相关层级的库存数据**，与创建时的扣减完全对称。

### 4.2 前置校验

- 订单状态必须为"待确认"、"待支付"或"已确认"才可取消
- 已入住、已离店的订单不可再取消
- 已取消的订单再次取消时，应按幂等成功返回，不重复返还库存

### 4.3 返还流程

```
取消订单 → 校验订单状态 → 返还库存 → 更新订单状态
                          ↓
              ┌───────────────────────────┐
              │ 1. 返还物理库存（增加可售量）│
              │ 2. 返还房价码配额（减少已售）│
              │ 3. 返还渠道配额（减少已售）  │
              │ 4. 返还市场码配额（减少已售）│
              │ 5. 返还渠道+房型配额（减少已售）│
              │ 6. 返还房价大类配额（减少已售）│
              └───────────────────────────┘
```

### 4.4 各层级返还规则

#### 物理库存返还

- **操作**：增加可售量
- **安全保护**：可售量不应超过"物理总房量 + 超预订量"的合理上限；如果超过，记录告警日志但仍执行返还（因为管理员可能已手动调整了物理房量）
- **超预订场景**：如果订单是在超预订状态下创建的（可售量曾为负数），返还后可售量恢复为正值，属于正常情况
- **逐日执行**：入住期间每天都要返还

#### 各维度配额返还

- **操作**：减少已售数量
- **防负数**：已售数量减少后不应低于 0
- **逐日执行**：入住期间每天都要返还
- **跳过规则**：如果该日期该维度没有设置配额上限，则跳过
- **条件执行**：与扣减时一致（市场码、房价大类有条件执行）

### 4.5 返还顺序

返还顺序与扣减顺序**相反**：

```
1. 房价大类配额（如有）
2. 渠道+房型配额
3. 市场码配额（如有）
4. 渠道配额
5. 房价码配额
6. 物理库存（最后返还）
```

### 4.6 返还的安全保障

| 风险 | 防护措施 |
|------|----------|
| 重复取消导致库存多返 | 订单状态校验 + 幂等性保证 |
| 已售数量减为负数 | 最小值保护，不低于 0 |
| 可售量超过合理上限 | 告警日志 + 允许超过（管理员可能已调整物理房量） |
| 取消的房间数与创建时不一致 | 从订单记录中读取房间数，不依赖前端传参 |

## 5. 并发控制要求

### 5.1 需要解决的并发问题

| 场景 | 风险 |
|------|------|
| 多个请求同时创建订单 | 超卖——两个请求同时判断库存充足，都成功下单 |
| 创建订单与取消订单并发 | 数据不一致——扣减和返还交错执行 |
| 多个取消请求并发 | 库存多返 |
| 可售性检查与扣减之间的时间窗口 | 检查通过后到实际扣减前，库存可能被其他请求抢占 |

### 5.2 业务层面的并发控制要求

1. **原子性**：可售性检查和库存扣减必须作为整体执行，中间不能被其他请求插入
2. **一致性**：所有层级的库存数据必须同时更新成功或同时失败，不允许部分更新
3. **幂等性**：同一订单重复提交不应重复扣减库存
4. **可重试**：并发冲突时，系统应自动重试而非直接报错

### 5.3 幂等性保证

- 使用订单号作为幂等键
- 扣减库存前，先查询该订单号是否已处理过
- 如果已处理，直接返回之前的处理结果
- 如果未处理，执行扣减并记录订单号

## 6. 异常处理规则

### 6.1 扣减失败

| 失败场景 | 处理方式 |
|----------|----------|
| 物理库存不足 | 回滚所有已扣减的库存，返回"库存不足" |
| 配额不足 | 回滚所有已扣减的库存，返回"配额不足" |
| 部分日期扣减失败 | 回滚所有日期的扣减，返回具体失败日期 |
| 系统繁忙 | 回滚，返回"系统繁忙，请稍后重试" |

### 6.2 返还失败

| 失败场景 | 处理方式 |
|----------|----------|
| 物理库存记录不存在 | 记录告警日志，跳过该日期 |
| 配额记录不存在 | 跳过（未设置配额 = 不限制） |
| 已售数量不足 | 最小值保护，不低于 0 |

### 6.3 数据修复

当库存数据出现不一致时（如系统崩溃导致部分扣减未完成），需要提供手动修复工具：

- 管理员可查看指定酒店和日期的各层级库存快照
- 对比订单已售数据与各层级已售数量，找出差异
- 提供一键修复功能，重新计算已售数量

## 8. 库存扣减 SQL 实现

### 8.1 物理库存扣减

物理库存扣减需要同时校验房型可售数和酒店可售数，确保不超过 min(房型可售数, 酒店可售数)。

**第一步：查询酒店可售数**

```sql
SELECT
    SUM(pi.available_rooms - pi.overbook_count) + IFNULL(ob.overbook_count, 0) AS hotel_available
FROM pms_inventory pi
LEFT JOIN overbooking ob ON ob.tenant_id = pi.tenant_id
    AND ob.hotel_code = pi.hotel_code
    AND ob.dimension_type = 'hotel'
    AND ob.dimension_code = ''
    AND ob.overbook_date = pi.inventory_date
WHERE pi.tenant_id = :tenantId
  AND pi.hotel_code = :hotelCode
  AND pi.inventory_date = :date
```

**第二步：扣减房型库存**

```sql
UPDATE pms_inventory
SET available_rooms = available_rooms - :roomCount,
    version = version + 1,
    updated_at = NOW()
WHERE tenant_id = :tenantId
  AND hotel_code = :hotelCode
  AND room_type_code = :roomTypeCode
  AND inventory_date = :date
  AND available_rooms >= :roomCount
```

- 影响行数 = 1：扣减成功
- 影响行数 = 0：库存不足，扣减失败

**第三步：应用层校验酒店可售数**

扣减房型库存前，需在应用层校验：`酒店可售数 >= :roomCount`，不足则拒绝。

**关键说明**：酒店可售数涉及多行聚合计算，无法在单行 UPDATE 的 WHERE 条件中高效表达，因此在应用层完成校验。整个校验+扣减过程在同一事务中执行，事务保证原子性。

### 8.2 配额扣减

```sql
UPDATE inventory_quota
SET sold_count = sold_count + :roomCount,
    version = version + 1,
    updated_at = NOW()
WHERE tenant_id = :tenantId
  AND hotel_code = :hotelCode
  AND dimension_type = :dimensionType
  AND dimension_code = :dimensionCode
  AND quota_date = :date
  AND quota_limit IS NOT NULL
  AND (quota_limit - sold_count) >= :roomCount
```

- `quota_limit IS NOT NULL`：只更新有配额限制的记录
- `(quota_limit - sold_count) >= :roomCount`：防止超额
- 影响行数 = 1：扣减成功
- 影响行数 = 0：配额不足或无记录，扣减失败

### 8.3 物理库存返还

```sql
UPDATE pms_inventory
SET available_rooms = LEAST(available_rooms + :roomCount, physical_rooms + overbook_count),
    version = version + 1,
    updated_at = NOW()
WHERE tenant_id = :tenantId
  AND hotel_code = :hotelCode
  AND room_type_code = :roomTypeCode
  AND inventory_date = :date
```

- `LEAST` 函数防止 available_rooms 超过合理上限

### 8.4 配额返还

```sql
UPDATE inventory_quota
SET sold_count = GREATEST(sold_count - :roomCount, 0),
    version = version + 1,
    updated_at = NOW()
WHERE tenant_id = :tenantId
  AND hotel_code = :hotelCode
  AND dimension_type = :dimensionType
  AND dimension_code = :dimensionCode
  AND quota_date = :date
  AND quota_limit IS NOT NULL
  AND sold_count > 0
```

- `GREATEST(sold_count - :roomCount, 0)` 防止 sold_count 变为负数
- `sold_count > 0` 确保只操作有已售数据的记录

## 9. 并发控制技术方案

### 9.1 方案选型

采用**数据库原子更新为主、乐观锁为辅**的混合方案：

| 机制 | 用途 | 说明 |
|------|------|------|
| 原子更新 SQL | 核心方案 | 将"检查+扣减"合并为一条 SQL，利用 InnoDB 行锁保证原子性 |
| `@Version` 乐观锁 | 辅助方案 | 复杂业务逻辑需要先读后写时使用，冲突时自动重试 |
| `@Transactional` | 事务保证 | 所有层级扣减/返还在同一事务中，任一失败全部回滚 |

### 9.2 原子更新原理

将"检查库存是否充足"和"扣减库存"合并为一条 UPDATE 语句：

```sql
-- 扣减：WHERE 条件中包含库存充足性检查
UPDATE pms_inventory
SET available_rooms = available_rooms - :roomCount
WHERE ... AND available_rooms >= :roomCount
```

- InnoDB 行锁自动保证同一行的并发安全
- 检查和更新在同一个原子操作中完成，不存在 TOCTOU 问题
- 无需额外的锁机制

### 9.3 乐观锁实现

为 `pms_inventory` 和 `inventory_quota` 表增加 `version` 字段：

```sql
ALTER TABLE pms_inventory ADD COLUMN version INT NOT NULL DEFAULT 0;
ALTER TABLE inventory_quota ADD COLUMN version INT NOT NULL DEFAULT 0;
```

JPA 实体中使用 `@Version` 注解：

```java
@Version
private Integer version;
```

当原子更新 SQL 不适用时（如复杂的业务逻辑需要先读后写），JPA 自动在 UPDATE 语句中加入 `WHERE version = :oldVersion`，冲突时抛出 `OptimisticLockException`。

### 9.4 事务隔离

整个库存扣减/返还操作必须在**一个数据库事务**中完成：

```java
@Transactional(rollbackFor = Exception.class)
public void deductInventory(InventoryDeductionContext context) {
    // 1. 逐日扣减物理库存
    // 2. 逐日扣减各维度配额
    // 任一步骤失败，整个事务回滚
}
```

事务隔离级别使用 MySQL 默认的 `REPEATABLE READ`，配合原子更新 SQL，足以防止超卖。

### 9.5 并发场景处理

**场景1：多个创建订单请求并发**

```
请求A: UPDATE ... available_rooms = 5-1=4 WHERE available_rooms >= 1 → 成功（行数=1）
请求B: UPDATE ... available_rooms = 4-1=3 WHERE available_rooms >= 1 → 成功（行数=1）
...
请求F: UPDATE ... available_rooms = 0-1=-1 WHERE available_rooms >= 1 → 失败（行数=0）
→ 请求F 事务回滚，返回"库存不足"
```

**场景2：创建与取消并发**

```
请求A（创建）: UPDATE ... available_rooms = 5-1=4
请求B（取消）: UPDATE ... available_rooms = 4+1=5
→ 两个操作串行执行（行锁），数据一致
```

**场景3：乐观锁冲突**

```
请求A: 读取 version=0, available=5 → 更新 available=4, version=1（成功）
请求B: 读取 version=0, available=5 → 更新 available=4, version=1（失败，version 已变）
→ 请求B 捕获 OptimisticLockException，重试
```

### 9.6 重试策略

对于乐观锁冲突，采用指数退避重试：

```java
@Retryable(
    value = OptimisticLockException.class,
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2)
)
public void deductInventory(InventoryDeductionContext context) {
    // 库存扣减逻辑
}
```

- 最大重试次数：3
- 初始延迟：50ms
- 退避倍数：2（50ms → 100ms → 200ms）
- 3 次重试后仍失败，返回"系统繁忙，请稍后重试"

### 9.7 幂等性实现

使用订单号（reservationCode）作为幂等键：

```
1. 扣减库存前，先查询该 reservationCode 是否已处理过
2. 如果已处理，直接返回之前的处理结果
3. 如果未处理，执行扣减并记录 reservationCode
```

存储方式：使用 `reservation` 表的 `reservation_code` 作为天然幂等键。

## 11. 旧版库存迁移方案

### 11.1 渐进式迁移

| 阶段 | 操作 | 风险 |
|------|------|------|
| 阶段1 | 新建 `InventoryDeductionService`，操作 `pms_inventory` + `inventory_quota` | 低（新增代码，不影响现有逻辑） |
| 阶段2 | `ReservationService` 切换到 `InventoryDeductionService`，停止操作 `inventory` 表 | 中（需充分测试） |
| 阶段3 | 废弃 `inventory` 表，清理相关代码 | 低（确认无引用后操作） |

### 11.2 数据一致性校验

切换前需校验旧版库存与 PMS 库存的数据一致性：

```sql
SELECT
    pi.hotel_code, pi.room_type_code, pi.inventory_date,
    pi.available_rooms AS pms_available,
    i.available_rooms AS old_available
FROM pms_inventory pi
LEFT JOIN inventory i ON pi.hotel_code = i.hotel_code
    AND pi.room_type_code = i.room_type_code
    AND pi.inventory_date = i.date
WHERE pi.available_rooms != IFNULL(i.available_rooms, -999);
```

## 12. 性能优化

### 12.1 批量操作

对于连住多晚的订单，可使用批量 UPDATE 减少数据库交互：

```sql
UPDATE pms_inventory
SET available_rooms = available_rooms - :roomCount,
    version = version + 1,
    updated_at = NOW()
WHERE tenant_id = :tenantId
  AND hotel_code = :hotelCode
  AND room_type_code = :roomTypeCode
  AND inventory_date IN (:dateList)
  AND available_rooms >= :roomCount
```

- 需校验影响行数 = 日期数量，否则说明某天库存不足

### 12.2 索引

确保以下唯一索引存在：

```sql
UNIQUE INDEX uk_pms_inventory (tenant_id, hotel_code, room_type_code, inventory_date)
UNIQUE INDEX uk_inventory_quota (tenant_id, hotel_code, dimension_type, dimension_code, quota_date)
UNIQUE INDEX uk_room_status (tenant_id, hotel_code, dimension_type, dimension_code, status_date)
UNIQUE INDEX uk_booking_controls (tenant_id, hotel_code, dimension_type, dimension_code, control_date)
```

### 12.3 缓存策略

| 数据 | 缓存策略 | TTL |
|------|----------|-----|
| 房态 | 本地缓存 | 30秒 |
| 预订规则 | 本地缓存 | 60秒 |
| 物理库存 | **不缓存** | - |
| 配额 | **不缓存** | - |

物理库存和配额数据不缓存，因为扣减/返还操作需要实时读写数据库。
